## 2026-07-20 脆弱性アラートの記載バージョンを影響範囲と混同した

### 何が起きたか

Snyk から「ws 8.21.0 に脆弱性あり」というアラートを受け、nuxtation の依存ツリーを確認した。
`pnpm why ws` の結果は 8.21.0 / 8.18.3 / 7.5.10 の3系統だったが、
「Snyk が指摘したのは 8.21.0 だから 7 系は対象外」と判断し、
`ws@8: ^8.21.1` というセレクタで **意図的に 7.5.10 を据え置いた**。

後からユーザーに他リポジトリの確認を依頼された際に CVE を直接調べたところ、
該当する CVE-2026-48779 (GHSA-96hv-2xvq-fx4p, High 7.5) の影響範囲は

```
>=1.1.0 <5.2.5 / >=6.0.0 <6.2.4 / >=7.0.0 <7.5.11 / >=8.0.0 <8.21.0
```

であり、**ws@7.5.10 はまさに影響下**だった。脆弱なバージョンを1コミット分そのまま残した。

### なぜ間違えたか

Snyk のアラートメールは「**新規に検出された issue**」のみを通知する。
これを「脆弱性の影響範囲そのもの」と読み替えてしまった。
7 系は Snyk が別タイミングで検出済み、あるいは未検出だっただけで、
安全であることの根拠にはまったくならなかった。

さらに「lighthouse の ws@7 を巻き込まないよう配慮した」という
**一見丁寧に見える判断**が、逆に脆弱性を温存する結果になった。
慎重さの方向を間違えると害になる。

### 次からのルール

1. **依存パッケージの脆弱性対応では、アラート本文のバージョン番号で判断しない。**
   必ず CVE / GHSA を引き、`affected range` を確認してから依存ツリー全体と突き合わせる。
   - 確認先: `https://github.com/advisories/<GHSA-ID>`
   - あるいは `npm audit` / `pnpm audit` で全系統を横断チェックする
2. **同一パッケージが複数メジャーで並存している場合、全系統を個別に判定する。**
   1つの系統を直したことで「対応済み」と結論しない。
3. **バックポート修正の有無を確認する。**
   古い系統にも patch リリースが出ていることが多い (今回は 7.5.11 / 6.2.4 / 5.2.5)。
   「メジャーを上げないと直らない」と決めつけない。
4. **依存を意図的に据え置く判断をしたら、その根拠を必ず検証してから書く。**
   今回はコメントに「lighthouse依存のws@7は対象外」と**誤った根拠を明記**してしまい、
   将来の自分や他者を誤導しかねなかった。

### 補足: pnpm overrides のバージョンセレクタ

`ws@8: ^8.21.1` のように書くと、解決済みバージョンが 8 系のものだけを対象に置換できる。
メジャーが混在する依存ツリーで特定系統だけを狙うときに有効。
ただし今回のように「狙い撃ちしたつもりが取りこぼす」リスクと表裏一体なので、
セレクタを絞るときは**絞った側が本当に安全か**を必ず確認すること。
